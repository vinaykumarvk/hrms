## 1. Source of Truth, Boundary & Traceability
Employee-review note. The current clickable screen reference is Prototype v2.1. A new config object — the Service-Catalogue master (owner: Service Desk Admin, M17) — was introduced; it has no export yet and is tracked in the Coverage Map (CFG-MAP-116) and Actions Register (CFG-012). A one-page convention for reading configuration across the PrimeSoft HRMS handoff package (prototype, Functional Specifications, and the Configuration Ownership & Coverage Map). Read this before interpreting any configuration screen or specification.

### Why this note exists
The tenant’s configuration is large (115 export files, several with 130–286 fields). No single artifact can both show it interactively and enumerate it completely without duplication and drift. This package therefore splits the job across three artifacts with clear, non-overlapping authority. This note states that split so a reader always knows which artifact to trust for which question.

### Source of truth — layered authority
| For this question… | The source of truth is… | Notes |
| What is configurable, and what are the current values? | The configuration export file (CSV) | The system export is authoritative for the field inventory and the tenant’s actual values. |
| What does a setting mean, how does it behave, what depends on it? | The Functional Specification (FS) | The FS specifies semantics, rules, dependencies, defaults and validation. It references the file; it does not re-print values. |
| Where is it managed, and what does the screen / flow look like? | The clickable prototype | The prototype shows the screen, its information architecture and interaction pattern, with representative data only. |

Rule of thumb: values → the file · meaning & behaviour → the FS · screen & flow → the prototype.

### Where the prototype stops and the document begins
The prototype carries the existence of a screen, its layout, its interaction pattern (list / add / edit), and a representative subset of rows and fields so the reader can see the shape. It never claims completeness — it does not enumerate every column or every row of a config file.
The document carries the full field inventory (by reference to the file), the semantics, dependencies, defaults, validation, and the coverage status.
In one line: the prototype is the shape and behaviour of a configuration screen; the document is the completeness and meaning of the configuration. A “representative” screen is intentional, not a gap — the build drives the screen’s full field set from the named config file.

### Traceability — one spine, read from any end
Every configuration item is traceable along a single chain:
Config file → Owning admin → Managing screen (page id) → FS reference (FR id) → Coverage status (Present / Partial / Missing)
This chain is carried by three devices:
The Configuration Ownership & Coverage Map — the index. One row per config file, with a stable ID (CFG-MAP-nnn), the owning admin, the managing screen (prototype page id), the FS reference, the coverage status, and a source-of-truth note.
Inline provenance lines — each configuration screen and each FS configuration section carries a short banner naming its source file and map ID, e.g. “Config source: Leaves_Settings_Export.csv · CFG-MAP-012 · screen is representative.”
This preface — read once, it tells the reader how the three artifacts relate.
Because the chain is bidirectional, a reader can start from any end: - From a file → the map gives the owning admin, the screen, the FS reference and the coverage status. - From a screen → its provenance banner cites the file and the map ID. - From the FS → each configuration section names the file and the screen.

### Coverage status — what the three values mean
Present — the screen manages the configuration at, or close to, the file’s field set; build follows the file for any remaining fields.
Partial (representative) — the screen exists and is correctly purposed, but shows a representative subset; the build drives the full field set from the named file. This is the expected state for most config screens and is not a defect.
Missing — the configuration exists in a file but has no managing admin screen; this is a genuine gap to be added.

### How to use this in review and build
Reviewers judge a config screen on purpose, ownership and interaction — not on whether every field is present (completeness is the document’s job, audited in the map).
Engineers build each config screen’s full field set from the named config file, using the FS for semantics and the prototype for the screen shape.
The map is the worklist: Missing rows are screens to add; Partial rows are field-completeness build tasks; Present rows are done.

## 4. Configuration Actions Register

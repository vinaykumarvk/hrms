## 0. Purpose & Non-Repetition Contract
References: BRD (authoritative for requirements); functional-spec-author non-repetition protocol.
This document is the single source of truth for the build-layer content shared across every module: API conventions, the validation library, the UI-state standard and component vocabulary, the scheduled-jobs index, the message catalogue, and the menu/navigation entitlement map. The governing rule is single source of truth — each fact lives in exactly one place. The BRD owns requirements, rules, the data model, the RBAC matrix, NFR targets, notification triggers, and state machines; this Foundation FS references them and authors only the build detail the BRD leaves out. Each module FS references the ids defined here and authors only what is unique to that module.
Where the BRD or prototype leaves a genuine gap, this document uses flag-and-recommend: it proposes a spec marked PROPOSED — confirm before build in §8 Open Items, never silently in the body.

## 1. API Conventions
References: BRD §6.2 (Standard Response Format), §6.3 (Rate Limiting), §6.4 (endpoint inventory), §7.4 (security NFR). Authored here: only the conventions the BRD does not state.
The standard success/error envelope is fixed by BRD §6.2 (JSON; 2xx with resource payload; 4xx/5xx with { error: { code, message, field, details } }) and rate limiting by BRD §6.3 — neither is restated here. This section adds the cross-cutting contract behaviour every module endpoint inherits and the BRD does not pin down.
| Convention | Rule (authored) |
| Versioning | All endpoints under /api/v1. Breaking changes ship under a new major prefix; additive fields are non-breaking. |
| Idempotency | All unsafe POSTs that create a transaction accept an Idempotency-Key header; a repeat within 24h returns the original result, not a duplicate. Required for workflow-initiating POSTs (leave/attendance/separation/offer). |
| Pagination | List endpoints use cursor pagination: ?limit= (default 25, max 100) + cursor=; response carries next_cursor. Offset paging is not used. |
| Sorting / filtering | `?sort=field:asc |
| Correlation id | Every request carries / is assigned X-Correlation-Id; it is echoed in the response and written to every audit and log line for the request (ties to BRD Appendix C). |
| Standard error codes | VALIDATION_FAILED (422), UNAUTHENTICATED (401), FORBIDDEN (403), NOT_FOUND (404), CONFLICT (409, incl. idempotency replays and state conflicts), PRECONDITION_FAILED (412), RATE_LIMITED (429), INTERNAL (500). Message copy behind each is in the §5 Message Catalogue (ERR-* ids). |
| Auth context | Bearer token carrying the session’s roles/entity scope (resolved per RBAC doc; enforced per Platform Spec P02). Endpoints never re-implement permission logic — they call the authorization service. |
| Effective-dating | Endpoints that mutate effective-dated fields accept effective_from; the change is staged and applied by JOB-M01-EFFDATE (see §4), not written live. Governed by BRD §4 / FR-M01-002. |

## 3. Global UI State Standard & Component Vocabulary
Shared interaction states (Batch-1 additions). Approval-gated field change — fields marked E·AR (e.g., PAN/Aadhaar/Passport/DL, bank) render read-only with a “Request change” control that opens a request dialog and routes to the owning approval workflow (e.g., sensitive-changes queue), never a direct write. Read-only mini-profile — the directory/org-chart drill-down surface; shows directory fields only (RBAC §11.2), no edit, no PII/compensation. Masked-own-view — the record owner sees Tier-1 IDs masked on screen but may export the full record unmasked.
References: BRD §7.7 (accessibility), §7.8 (browser/platform); the design system for visual tokens. Authored here: the behavioural standard every screen inherits.
Every screen implements the five canonical states so module FS need not re-describe them: empty (no data — show purpose + primary action, never a blank panel), loading (skeleton, no layout shift), error (inline message from an ERR-* id + retry; never a raw stack/500), no-permission (the gating menu item is hidden per §6; a deep-linked forbidden resource shows ERR-FORBIDDEN, not a 404 leak), and partial-data (render what is authorised, mask the rest per RBAC field access — never fail the whole screen).
Shared component vocabulary (referenced by id from module field tables): inline-edit field, effective-dated field (shows current + staged value), masked field (PII per RBAC §3.9 / Platform P02), multi-step wizard, list+filter+bulk-action toolbar, approval action bar (approve/reject/send-back/delegate, labels per workflow stage aliases), attachment control (VAL-FILE), comment box (VAL-COMMENT), date/effective-date picker, and the read-only audit trail panel. Visual styling is the design system’s job, not this document’s.

## 4. Scheduled Jobs & Background Processing — Index & Shared Standard
References: BRD §4.14 jobs, Appendix C (audit), Appendix D (workflow). The job RUNNER infrastructure (scheduler, retry, isolation) is owned by Platform Spec §X.1; each job’s CADENCE and LOGIC are owned by the module FS §7/§8 cited below. This Foundation section owns the consolidated INDEX and the shared failure/observability standard so nothing is scattered.
Shared runner standard (authored once, inherited by every job): every job is idempotent (safe to re-run; duplicates prevented by a per-period run key in jobs); retries with exponential backoff up to 3 attempts; on terminal failure emits JOB-FAIL → alert MSG-SYS-JOBFAIL (§5) to the owning-module admin + platform ops; runs per-tenant in isolation; takes a period lock against concurrent user writes where it mutates balances or closes a period; and writes one audit row per run (correlation id, rows affected, outcome) per BRD Appendix C. Exact cron/timezone for each job lives in its module FS.

## 5. Message Catalogue

Authored here: the catalogue CONVENTIONS, the SHARED/SYSTEM messages used by every module, and the MASTER INDEX. Module-specific message COPY is authored in the module FS slice cited and referenced by id — not duplicated here.
Conventions. Channels and recipients per BRD §9 (never restated). Id scheme: MSG-<module>-<n> for notifications, ERR-<area> for user-facing error copy; system messages use MSG-SYS-*. Templates carry typed merge fields {like_this}. Severity: info / warning / error. A screen state (§3) or API error code (§1) references an id; it never inlines copy.

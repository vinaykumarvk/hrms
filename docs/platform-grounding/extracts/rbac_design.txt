# 1. Overview
Access control in PrimeSoft HRMS operates at four layers, applied in combination for every user session:
| Layer | What It Controls |
| Module-Level | Whether a module is visible at all. Inactive modules are fully invisible — not just disabled. Includes a distinct Module Admin tier for configuration rights. |
| Field & Section Level | Visibility and editability of individual fields and form sections within a module. |
| Data-Level (Row-Level Security) | Which records a role can see — scoped by reporting chain, department, contribution level, or entity. |
| Action-Level | What a user can do within a record: View Only · Edit · Approve/Reject · Download · Admin Rights. |

PII Protection Ceiling. PII fields carry system-enforced protection ceilings. No Organisation Admin, Module Admin, or any other role can override these ceilings upward. All references to PII restrictions elsewhere in this document operate subject to this ceiling. Exceptions are explicitly stated as platform-level grants (e.g. Office Admin national ID access) and are fixed — not configurable.
Conflict Resolution Rule. Where a user holds more than one role simultaneously, the more restrictive permission always applies. A less permissive role never elevates access granted by a more permissive one.
All rules are stored as configuration data.

## 2.1.1 Configuration ownership — build vs bind (added v1.1)
References: §2.1 (Platform Roles), §4 (Module-Level Admin Rights); BRD §3.2; Platform Spec §W.1/W.2/W.3 + P02 (enforcement).
Organisation Admin is the single tenant-level owner of all reusable configuration definitions: process flows / workflows, approval flows, skip and SLA settings, decision matrices, form and custom-field definitions, notification configuration, field-level RBAC, integration credentials, and SSO. Entity-scoped HR Admin and the module admins do not build these definitions — they bind a pre-built flow or form to an operational policy or transaction within their own entity (e.g. attaching an approval flow to a leave policy, or selecting a form on a leave type). Platform Super Admin owns cross-tenant provisioning, platform master data, and migration tooling — not the day-to-day configuration builders.
How this is enforced at runtime is specified in Platform Spec P02; the builder screens are specified in the Org Admin — Configuration FS and the binder screens in the HR Admin FS. Reconciliation note: BRD §3.2 lists workflow configuration and field-level RBAC under Org Admin but omits form and notification configuration; this section closes that gap — see Open Item OPEN-RBAC-02.

# 3. Data-Level Access — Scoping Rules

## 3.1 Scoping Dimensions
Five dimensions can be combined to define what records a user can see:
Reporting Chain — Manager roles see records of their direct and indirect reports only. Skip-level Managers see their full subtree but cannot approve or edit.
Department — HOD sees all employees in their assigned department regardless of reporting line.
UserAssignment Group — A named group of one or more employees assigned to a specific individual. UAG Head has the same entitlements as HOD scoped to their group, with the exception of workflow approval authority — see §3.5.
HRBP Assignment — Business unit assignment is optional. HRBPs are assigned employees directly — individually or via UAG. Data scope limited to directly assigned employees, further refined by entitlement dimensions — see §3.3.
Contribution Level — An additional filter applied within a role’s normal scope. Contribution levels are:
| Level | Description |
| Intern | Entry-level, fixed-term learning engagement |
| Associate | Junior professional — early career |
| Individual Contributor | Mid-level professional — independent delivery |
| Lead | Senior professional — leads work, may guide others |
| Senior Lead | Senior specialist or team lead — cross-functional scope |
| Manager | People manager — direct reports |
| Senior Manager | Senior people manager — manages managers |
| CEO | Organisation head |

Contribution levels are used in performance calibration scoping, hike recommendation banding, and recruitment entitlement configuration.
Configuration note. Contribution levels are a RBAC scoping dimension. The tenant-level master mapping of designation/grade to contribution level is Org Admin configuration. Individual employee contribution level on the employment record is editable by HR Admin (direct edit — see §7).
Entity — HR Admin, Finance Admin, and Office Admin are scoped to their single entity. Cross-entity access requires explicit privilege granted by Organisation Admin and is audit-logged.
Individual Entitlement — Time-bound access beyond a role’s default profile, granted by Organisation Admin within PII protection ceilings (see §1).

## 3.2 Individual Entitlements
The authoritative narrative is in Product Vision §3.2 (Individual User Entitlements). The five dimensions across which individual entitlements operate are reproduced here for accessibility.
| Entitlement Type | Example Use Case |
| Department-level grant | HRBP temporarily covering a specific department |
| Field-level grant | Senior HRBP granted view of salary band (not individual CTC) for benchmarking |
| Section-level grant | Legal counsel granted access to the employment contract section for compliance review |
| Module-level grant | Senior Manager granted read access to Analytics for their assigned group |
| Contribution-level uplift | VP-level Manager granted visibility of Senior Manager-level direct reports during a reorg |

Operating rules. All individual entitlements require Organisation Admin approval, are audit-logged, carry a mandatory expiry date, are automatically revoked on expiry, and are subject to PII protection ceilings (see §1).

## 3.3 HRBP — Entitlement Scope
An HRBP’s data scope is defined by direct employee assignment — individually or via UAG. Within that assigned population, access is governed by all five entitlement dimensions:
| Entitlement Dimension | Default | Configurable by Org Admin? |
| Contribution level | All contribution levels within assigned employees visible | Yes — can be restricted to specific levels |
| Department | All departments within assigned employees | Yes — can be restricted to specific departments |
| Field level | Standard HR fields visible; compensation fields hidden | Yes — within PII protection ceiling (see §1) |
| Section level | Employment and lifecycle sections visible; compensation section hidden | Yes — within PII protection ceiling (see §1) |
| Module level | HR operational modules within entity | Yes — additional module access via individual entitlement only |


## 3.4 Office Admin — Access Scope
The Office Admin role is strictly scoped to entity level:
| Access Type | Detail |
| Entity scope | Single entity only — Office Admin in Entity A cannot access employees in Entity B |
| Employee Directory | Same as standard employee directory — name, profile photo, designation, department, official email, official phone, office location, reporting manager |
| Date of Birth | View only — all employees within the entity |
| National Identity Documents | View and upload — PAN, Aadhaar, Passport Number, and Driving Licence. Cannot delete. Field values and identity documents are treated as the same — no distinction between field value and document. All four are platform-level grants for Office Admin — fixed, not configurable by Org Admin upward or downward. Changes to any field value require HR Admin approval via workflow before the change is committed (E · AR per §7). |
| Bank Account Entry | Enter and update employee bank account details — direct write, no approval workflow required. Cannot view full account numbers — masked to last 4 digits after entry. All entries and updates are audit-logged. |
| All other data | No access |

National ID and DOB access are explicit platform-level grants — fixed and not configurable upward or downward by Org Admin.

# 4. Module-Level Admin Rights

## 4.1 Design rules
Module Admin rights do not expand a role’s data scope or PII access ceiling (see §1).
Admin capabilities are configurable at the individual Module Admin user level — within the same module, different Module Admin users can hold different subsets of admin capabilities as granted by Organisation Admin.
Every module must have at least one designated Module Admin.
Distinct Module Admin roles inherit the action rights (View, Edit, Approve/Reject, Download, Admin) of their assigned module scope. They do not appear as separate columns in the action matrix — their access within their module is equivalent to HR Admin scoped to that module only.
Module Admin roles have no access outside their assigned module unless an individual entitlement is explicitly granted by Organisation Admin (§3.2).
Joint ownership modules (M07, M10) require both designated admins to be assigned — neither role alone constitutes full module admin coverage.

## 4.3 Capability Flag Registry
Capability flags are grantable extensions to existing roles. A flag is NOT a role — it is an opt-in capability that an Organisation Admin grants to a specific user’s existing role assignment. Grant and revoke events are audit-logged.
| Flag | Grantable on | Capability granted | Capability NOT granted | Governance |
| BGV review | Onboarding Admin · HR Admin | View Verification Reports tab on candidate records · view vendor BGV results per check (Verified · Discrepancy · Pending · Unable to Verify) · record disposition on Discrepancy alerts (retain · investigate · initiate separation) · view BGV result history on Employee Profile post-completion | Edit candidate-submitted form fields (per M02 §A.1 ‘Allow BGV Admin to edit user inputs’ = No) · view BGV results for employees outside the role’s existing data scope · approve onboarding completion (governed by Onboarding Admin / HR Admin role, not by this flag) | Organisation Admin only. Grant and revoke both audit-logged to P05. Capability survives role transitions only if the destination role is in the ‘grantable on’ list — otherwise revoked automatically with notification to Org Admin. |
| Letter Admin | Document Admin · HR Admin | Author and manage letter templates in the M11 letter template register · configure merge-field bindings · designate additional editors per template · approve template content for activation · publish and unpublish templates · manage template versioning | Edit policy library content (governed by Document Admin role, not by this flag) · manage employee document vault contents · alter retention or disposal rules · access documents outside the role’s existing data scope | Organisation Admin only. Grant and revoke both audit-logged to P05. Capability survives role transitions only if the destination role is in the ‘grantable on’ list — otherwise revoked automatically with notification to Org Admin. |
| Asset Custodian | IT Admin · IT Asset Manager | Hold custodial responsibility for a set of assigned assets · confirm periodic asset audit for held assets | Edit the asset register · reassign or write-off assets (IT Admin only) | Organisation Admin only; grant/revoke audit-logged to P05. |
| Department Head — Asset Audit Certify | HOD / UAG Head | Certify the periodic asset-audit attestation for the department’s assigned assets | Edit the asset register · reassign/write-off (IT Admin only) | Organisation Admin only; audit-logged to P05. |

Configurable role grants (added v1.2). Two HOD grants are configured per user by Org Admin rather than as binary flags, because they are scoped per-user / per-workflow: (a) HOD report visibility (off by default, enabled per HOD user) and (b) per-workflow approval authority (off by default, enabled per HOD user per workflow type). Both are audit-logged to P05. Together with the four flags above, this is the complete Phase-1 capability/grant inventory. Change Manager is not a Phase-1 flag.
Design rule. Capability flags are introduced sparingly. The bar for introducing a new flag is: the capability must be narrow and bounded (single data surface or action set), must not justify role proliferation, and must align with the Module Admin tier pattern where the parent role exists. Future modules adding new flags must register them here in §4.3.

## 4.4 RBAC Administration Surface — prototype screens (added v1.4)
RBAC is administered through two screens in the Org Admin configuration hub. These screens are the management surface for the access-control model defined in this document; they do not redefine it. The authoritative permission depth is §5 of this document and the StandardPermissionsExport files (CFG-MAP-053…060); the screens present that model representatively, consistent with the configuration source-of-truth convention (values and full inventory → the export and this document; screen and interaction → the prototype).
RBAC roles & permissions — cfg-rbac (FR-P02-001). The landing screen. It lists the standard roles (role, scope / assignee context, permission count, users assigned) with an action to open each role for modification, and renders a role × permission matrix covering every module group (Employee Master, Onboarding, Exits & Offboarding, Leave, Attendance, Recruitment, Performance, Documents, Assets & IT, Org & Platform configuration, RBAC & Security) against the key roles, using the §5.1 legend. The on-screen matrix carries the key actions per module for at-a-glance “who can do what”; the exhaustive per-permission inventory remains §5.1 and the per-module FS. Org Admin is the only role that can modify; HR Admin and functional admins reach the screen read-only via the configuration-hub fallback. A provenance banner names the source files and the map IDs.
Role permission editor — cfg-rbac-role (RBAC §4.4). Opened by selecting a role (or “New role”). It is the screen through which a role is modified, and has two parts. (a) Role definition — role name, status, assignee context / scope (Self · Team · Department · Entity · All tenants), standard-vs-custom type, and description. (b) Permissions by module — one section per module group, each listing that module’s actions (View · Add · Edit · Delete · Approve · Export and module-specific actions) with an allow / deny toggle and a per-action scope selector, plus a per-module “enable all”. Saving updates the role policy and writes a change entry to the P05 audit log (actor, role, permissions changed, timestamp); sensitive grants (compensation, audit, RBAC, platform enforcement) follow the maker–checker rule where configured. The toggle and scope set shown are representative — the complete action set per module is governed by §5 of this document and the module FS.
Boundary. Role definition lives in these Org Admin screens (cfg-rbac / cfg-rbac-role). Platform-level enforcement and security posture live in Platform Super Admin (psa-security, Platform Spec P02). These administration screens are tagged to this section (RBAC §4.4); they are distinct from the Platform Spec P02 enforcement requirements FR-P02-001 (authorization resolution) and FR-P02-002 (field-level enforcement), which the screens bind but do not implement. The configurable per-user grants in §4.3 (capability flags, HOD report visibility, per-workflow approval authority) are administered through the same role/grant surface and remain audit-logged to P05.

# 12. Role Permission Summaries

## 12.1 Employee
View and edit own profile (limited fields) · apply for leave · view leave balance and history · view own attendance and submit regularisation · view and download own payslips and tax documents · submit expense claims (Phase 3) · self-review in performance appraisal · access Chat Agent (policy queries only) · view employee directory and org chart · view own analytics. Cannot view any other employee’s compensation, payslip, leave, or attendance data. Leave type selector shows only types with available balance — zero-balance types are hidden. SPL has zero quota by default and does not appear in the selector until Leave Admin or HR Admin credits a balance.

## 12.2 Manager (L1)
View personal and employment details of direct and indirect reports · approve/reject leave and attendance requests · edit team attendance and assign shifts · view team timesheets and schedules · review team performance · view team-level analytics. Cannot view salary, CTC, payslips, bank details, compensation bands, or government IDs of any employee.

## 12.3 HOD
Read-only view of all employees in their department · view attendance (no edit or approval actions) · view workflow lifecycle tab · view analytics scoped to department with toggle between reporting chain view and entire department view. Team leave not shown on calendar — HOD uses the team leave dashboard. Dashboard fields: employee name · leave type · from/to dates · status · reporting chain position. Compensation and published ratings visibility off by default — see §6. Workflow approval authority off by default — Org Admin can enable per workflow type per individual HOD user.

## 12.4 UAG Head
Same as HOD scoped to assigned UserAssignment Group. Compensation visibility off by default — configurable per user by Org Admin. Published ratings visibility off by default — configurable per user by Org Admin. Workflow approval authority: hard ceiling — cannot be granted under any configuration. See §3.5.

## 12.5 HRBP
View and edit attendance for directly assigned employees · approve/reject leave requests and attendance requests for assigned employees · view all lifecycle workflow events for assigned employees · view analytics scoped to assigned population. Business unit assignment optional — employee assignment (individual or via UAG) is the primary scoping mechanism. Access governed by entitlement dimensions — see §3.3. No payroll, CTC, or compensation access.

## 12.6 Office Admin
Access strictly limited to entity level: employee directory · date of birth (view) · national identity documents (view and upload — PAN, Aadhaar, Passport Number, and Driving Licence) · bank account details (entry and update — direct write, no approval required, masked after entry). See §3.4. No access to payroll, payslips, compensation, performance, leave, attendance, or recruitment data.

## 12.7 HR Administrator
Full access to all employee records within their entity · full lifecycle management · payroll initiation (Finance Admin approval required before disbursement — see §4) · statutory compliance outputs (Phase 2) · policy and document management · recruitment oversight · audit log access · Module Admin rights across all HR modules.
HR Administrator is eligible for two capability flags: the BGV review flag and the Letter Admin flag (see §4.3). When the BGV review flag is granted, HR Admin gains the BGV-specific capabilities listed in §4.3 — without the flag, HR Admin does not see the Verification Reports tab and cannot record disposition on BGV Discrepancy alerts. When the Letter Admin flag is granted, HR Admin gains the letter-template-management capabilities listed in §4.3 — without the flag, HR Admin does not have author / publish rights on the letter template register (those remain with Document Admin by default). Neither flag is auto-granted — Organisation Admin must explicitly grant each.

## 12.8 Finance Admin
Payroll run approval · view and download individual payslips · payroll aggregates and cost centre data · view compensation bands for budgeting · joint M10 module admin rights for configuration purposes alongside Compensation Admin — Finance Admin does not appear in the hike approval workflow at any stage (see §9). Cannot view personal PII fields outside the payroll approval context.

## 12.9 CEO
Final approver for hike and compensation decisions (see §9). No other system permissions beyond standard Employee self-service access unless additional roles are assigned.

## 12.10 Onboarding Admin
Onboarding Admin is a distinct Module Admin role scoped to M02 only, entity level. Capabilities (configurable per individual user by Organisation Admin):

Configure document clusters — Sign-Off · Undertaking · Reference (per-document employer signature; per-cluster auto-rejection on DOJ change)
Configure onboarding workflows — stages · assignees (role · user · UAG · manager · HRBP · HOD) · SLA · escalation · skip conditions
Configure welcome page (Group Company display)
Configure email templates (invitation · reminder · completion notifications)
Manage BGV vendor profiles — capability subset under Onboarding Admin
Assign verification packages (Onboarding BGV · ID Verification · Trigger Verification) to onboarding processes
Configure auto-initiation rules (enabled · DOJ-based · 14 days before DOJ)
Configure mandatory initiation attributes
Initiate onboarding for candidates · approve/reject candidate fields and documents · send back onboarding · complete onboarding
Assign Key People (Buddy · Teammates · Onboarding SPOC · Recruiter)
Optional capability flag (granted separately by Org Admin): BGV review — see §4.3.
Boundaries. Onboarding Admin has no access to payroll, compensation, performance, leave, attendance, or recruitment data outside the onboarding context. Cannot edit candidate-submitted form fields directly — admin actions are limited to approve / reject / send back. Data scope: entity level; subject to entitlement dimensions per §3.2.

## 12.11 Offboarding Admin
Configure FnF clearance workflows · manage exit interview templates and separation checklists · track offboarding task completion. Entity level. FnF payroll settlement remains with HR Admin and Finance Admin. No access to payroll, compensation, performance, or recruitment data.

## 12.12 Leave Admin
Configure leave types, policies, and accrual rules · override leave balances · manage holiday calendar · manage Leave Settings jointly with HR Admin and Org Admin · approve and reject individual leave requests · edit leave records · raise leave on behalf of any employee within entity scope · revoke approved leave directly or approve employee revoke requests. Entity level. Leave encashment case-by-case authorisation is HR Admin only — Leave Admin cannot authorise individual encashment requests. No access to payroll, compensation, attendance configuration, or performance data.
Leave approval flows.
Standard flow: Leave Admin is an eligible approver at any stage alongside Manager (L1), HRBP, and HR Admin.
Two-stage flow (ML · SPL · SBL): Leave Admin is a Stage 2 eligible approver alongside HRBP and HR Admin — Stage 2 is mandatory.
Escalation: Leave Admin is notified simultaneously with next level manager and HRBP / HR Admin when SLA is breached (10 days).
Revocation: Leave Admin can revoke directly or act on employee revoke requests — Managers cannot revoke under any circumstances.
Leave type visibility — platform-enforced rules.
During probation: only Unpaid / LOP available. All other leave types hidden.
During notice period: only Sick Leave (if balance > 0) and Unpaid / LOP available. All other leave types hidden.
Zero-balance leave types are never shown in the selector. Unpaid / LOP always shown regardless of balance.

## 12.13 Attendance Admin
Configure shifts, rosters, and attendance policies · manage biometric device mapping · lock and unlock attendance periods · override punch records · approve and reject all attendance request types (regularisation, out duty, shift change, planned overtime) for all employees within the entity. Attendance Admin is an eligible approver at any stage of the standard attendance flow alongside HRBP and HR Admin. Attendance escalation fires after 5 days — on 24th and 25th of each month, escalation cadence overrides to 2-hourly notifications. Entity level. No access to payroll, compensation, leave configuration, or performance data.

## 12.14 Payroll Admin
Initiate payroll runs · manage salary structures · generate disbursement files. Finance Admin approval required before disbursement files are released (see §4). Entity level. No access to performance ratings, recruitment pipelines, or personal PII fields outside payroll context.

## 12.15 Compliance Admin
Manage statutory rates, thresholds, and compliance parameters jointly with HR Admin · generate statutory compliance outputs. Entity level. Joint ownership with HR Admin for M07 — see §4. No access to recruitment, performance, or individual employee personal data beyond compliance filing requirements.

## 12.16 Performance Admin
Configure appraisal cycles · manage goal frameworks · initiate and close performance cycles · manage calibration sessions. Entity level. Subject to contribution level, department, field, and section entitlement configuration per user by Org Admin — see §8.3. Draft ratings and PII restrictions apply regardless of entitlement — see §6.

## 12.17 Compensation Admin
Configure hike cycles · manage grade bands · manage compensation revision workflows jointly with Finance Admin. Entity level. Joint ownership with Finance Admin for M10 — see §4. Does not approve hike decisions — CEO is the defined approver (see §9). HR Admin initiates the hike cycle. No access to individual payslips or personal PII fields.

## 12.18 Analytics Admin
Create and publish custom report definitions · schedule report delivery · manage dashboard layouts. Configuration rights entity level. Analytics module available to all users — Analytics Admin does not control who can access analytics. Data visibility for every user governed by their own role entitlements.

## 12.19 Document Admin
Document Admin is a distinct Module Admin role scoped to M11 only, entity level. Capabilities (configurable per individual user by Organisation Admin):
Configure the policy library register — policy categories, applicability rules, version control
Manage policy clusters and acknowledgement requirements (single global acknowledgement text; per-template override deferred to Phase 2)
Configure the letter template register and merge-field bindings (per M11 §D)
Manage employee document vault settings — storage policies, retention windows (7 years post-exit baseline · indefinite for acknowledgement records), disposal rules
Configure the sign-off and acknowledgement engine — including non-repudiation backbone
Manage versioning rules (per M11 §H)
Manage visibility and access control profiles (per M11 §F)
Manage POSH compliance records
Optional capability flag (granted separately by Org Admin): Letter Admin — see §4.3.
Boundaries. Document Admin has no access to payroll, compensation, performance, leave, attendance, recruitment, or onboarding data outside the document-management context. Cannot edit business rules of consuming modules (M02, M03, M08, M09 own their respective business semantics; M11 owns only the document substrate per the M11 module boundary statement). Data scope: entity level; subject to entitlement dimensions per §3.2.

## 12.20 Recruiter
View and manage assigned requisitions and candidate pipelines only · schedule interviews · initiate BGC · limited directory access (name, designation, department, official email only). Cannot generate offer letters. See §8.1 for full scoping rules.

## 12.21 Recruitment Admin
Full pipeline visibility · generate offer letters · assign recruiters · configure job boards and agency access · recruitment reporting. Subject to entitlement configuration — see §8.2. Individual admin capability subsets configurable per user by Org Admin.

## 12.22 Skip-level Manager
Read-only view of full reporting subtree — personal and employment details only. Participates in calibration sessions. Retains read access to published ratings for full subtree after calibration window closes — see §6. No edit, approval, or download actions on operational data.

## 12.23 Dotted Line Manager
Read-only view of dotted-line reportees — personal and employment details only. View policy documents. View team assets. No edit, approval, or payroll access.

## 12.24 IT Admin
Asset master management · device assignment and return · IT provisioning tasks linked to onboarding · FnF asset clearance. Cannot view employee personal or employment data beyond asset assignment requirements.

## 12.25 Candidate / Pre-joining
See §3.6 for full state definitions, access scope, and transition rules.

## 12.26 Contractor / Consultant
Status: To Be Decided. Interim assumption: own attendance and document access scoped to engagement period. No payroll visibility. Not included in employee directory.

## Manager-role review (Round 3)
Bulk-action permission: a bulk approve/reject/delegate requires the same permission as the single-item action on that queue — no separate grant. Bulk actions are audit-logged per item.
Manager notice-period edit: a new permission governs a manager/reviewer editing the notice period during manager-initiated separation (distinct from the existing edit Recovery Days flag). Default off; configurable in Notice settings.
Workspace exclusivity: the Admin workspace is exclusive — admin permission roles do not surface Employee/Manager screens while the user is acting as Admin. Workspace availability = held permission roles + has-reportees flag. See OPEN-FS-FND-05 (BRD §3.4 reconciliation).

## Manager-role review (Round 3 follow-up)
Admin-workspace exclusivity (OPEN-FS-FND-05 resolved). Holding an admin permission role grants an exclusive admin workspace: while acting as Admin the user sees only admin functions; the employee self-service surface is not rendered. Employee/Manager/HOD/CEO retain self-service. Workspace availability = held permission roles + (derived) has-reportees flag.
Manager on-behalf action gating. In the employee-context (reportee) view the manager sees the employee's full structure but may perform only the actions their role permits on a reportee (approve regularisation/leave, apply-on-behalf where allowed, rate/comment on performance, initiate probation/separation). All on-behalf actions are audit-logged with both actor and subject.
Reportee field visibility. The reportee view shows the same information the employee sees, except the intentional masks (full Aadhaar/PAN, bank account number, statutory IDs) — restricted to the employee and authorised HR/Finance roles. This supersedes the earlier "manager = HOD narrow scope (§3.9)" restriction on the manager reportee record.

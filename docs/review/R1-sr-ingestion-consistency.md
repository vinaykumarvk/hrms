# R1 — Digital Service Register (G12) Ingestion-Contract Consistency Review

**Scope:** One cross-cutting concern — does every module that writes to the G12 Digital Service Register (SR) ledger call the *same* governed ingestion contract, with event types, idempotency/dedup keys, reversal semantics, provenance, ledger-entity naming, and tenant scoping that are mutually consistent?

**Owner reviewed:** `docs/brd/v3/G12-digital-service-register.md`
**Writers reviewed:** G04, G05, G06, G08, G09, G10, G11
**Grounding:** `docs/brd/PLATFORM_FOUNDATION.md`, `docs/brd/MODULE_RECONCILIATION.md`
**Date:** 2026-07-01 · **Reviewer:** integration-reviewer (evidence-first, report-only)

---

## Verdict — **MATERIAL CONFLICTS**

G12 *does* define a single, explicit, well-engineered write-port (`POST /api/v1/sr/ingest`, the "only write path", with syntactic `(source_module, source_reference_id, source_event_version)` + semantic `fact_key` dedup, a reversal envelope, a `source_module` provenance allowlist, a versioned `sr_event_type` taxonomy, and a `tenant_id`-scoped per-employee hash chain). The **ledger entity name (`service_register_events`) and its net-new-on-P05 character are consistent across all eight files** — that part is clean, and **G09 is a reference-quality writer that matches the owner contract end-to-end** (endpoint, syntactic tuple, `fact_key`, `source_module=G09`, `is_reversal`/`reverses_source_reference_id`, `*_REVERSAL` taxonomy, supersede-not-delete).

But the **integration contract does not actually line up**: (1) the write-port **URL differs** — G12 says `/api/v1/sr/ingest`, while G04 and G05 both call `/api/v1/sr/events`; (2) the **idempotency/dedup key is reinvented per writer** and the canonical syntactic-tuple fields are not populated by anyone except G09; (3) `fact_key` — which G12 makes **mandatory for qualifying-service-bearing events** (`SR_FACT_KEY_REQUIRED`) — is absent from G04/G05/G06/G10, the very modules whose events count toward pension; (4) G05 invents a `COMPENSATING` reversal event type that is not in G12's taxonomy; and (5) the **writer set and G11's write/read role are stated four different ways** across G12 and the reconciliation doc. These are wiring-level mismatches that would fail at first integration and partially defeat the anti-double-counting guarantee. Hence **MATERIAL CONFLICTS**, not minor drift.

## What is already consistent (no action)

- **Ledger entity name & character:** all eight files name the ledger `service_register_events`, attribute ownership to G12, and describe it as net-new on the P05 audit/immutability substrate (DB-trigger, immutable, ≥7-yr) — **consistent** (F-14 is only a wording nit). (G12 L392; G04 L310; G05 L294/L711; G06 L279; G08 L223/L232; G09 L264; G11 L189.)
- **Append-only / supersede-not-delete:** no writer hard-deletes; corrections are new rows. The *mechanism names* drift (F-04), but the no-hard-delete invariant holds everywhere. (G12 rule 9 L793; G05 L764; G06 L994/L2082; G08 L1493; G09 L793.)
- **G09 is the reference implementation:** matches the owner contract on endpoint intent, syntactic tuple, `fact_key`, `source_module`, reversal envelope, and supersession — use it as the template to bring the other writers into line.

---

## Recommended remediation order

1. **F-01 + F-06 (one amendment):** freeze the canonical write-port URL and the canonical writer matrix in G12 FR-01/FR-02; mirror in Reconciliation §D.
2. **F-02 + F-03:** make `fact_key` and the `(source_module, source_reference_id, source_event_version)` tuple required on every writer's ingest call (acceptance-tested).
3. **F-05:** resolve G11 writer/consumer and name the owner of the separation/superannuation event.
4. **F-04 + F-07 + F-08:** publish the missing `sr_event_type` codes (incl. an appraisal mapping) and replace `COMPENSATING`/`AMENDMENT` with the G12 reversal envelope.
5. **F-09–F-14:** payload-field and wording fixes (provenance, tenant scoping, direct-write framing, 503 residue, platform-primitive nit).

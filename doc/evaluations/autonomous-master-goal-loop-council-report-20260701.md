# Council Evaluation: Single master `/goal` looping over a file of phase sub-goals for unattended end-to-end execution

*2026-07-01 · Framed question: Would encoding every phase/sub-phase `/goal` prompt into one JSON/YAML file and running ONE master `/goal` that loops over the sub-goals (optionally clearing memory between them) run the whole AI Dev Pipeline (PH-00..PH-10, with hard dependencies, human review gates, exit-criteria, and code/schema that must stay green) unattended end-to-end? Failure modes / better alternatives?*

## Chairman's Verdict

### Where the Council Agrees (highest confidence)
1. **Keep the declarative file.** Encoding the phase prompts as a durable, reviewable, version-controlled JSON/YAML manifest is the genuinely good move — all five advisors endorse it as *input*.
2. **The single master `/goal` loop is the wrong engine** for unattended end-to-end. Even the Proponent reframes to "not one `/goal` to rule them all but a manifest-driven runner." The literal proposal does not survive.
3. **Three root causes converge:**
   - **Context exhaustion** — one session cannot carry PH-00A..PH-10; the 447-table schema + contracts + tests already saturate context, and auto-compaction silently drops the exit-criteria/evidence rules the envelopes depend on. (The "optionally clear memory" clause is itself an admission the run won't fit.)
   - **Self-certification / reward-hacking** — a `/goal` Stop hook can only enforce a *machine-checkable predicate*. When the same agent that did the work also grades "done," "blocks until the condition holds" degrades into "blocks until the agent says yes." The cheapest way to satisfy "all subgoals complete" is to declare completion or weaken a failing test to green.
   - **Structural conflict with gates** — `/goal` is engineered to *prevent* halting; a human review gate *requires* halting. One master `/goal` doesn't skip gates, it fights them.
4. **The right structure** is one bounded run **per sub-phase**, driven by an **external orchestrator** (bash driver now → CI / scheduled agent later), with **exit-criteria expressed as executable commands** (return 0/1) run **outside the model**, advancing only on green + `gate:auto`, **halting at `gate:human`**, **checkpointed/resumable from phase N** (never restart PH-00 — spend caps have been hit), memory clearing for free per fresh session.
5. **"Unattended" is honestly "unattended up to the next gate, then parks."** A relay race that pauses, not fire-and-forget.

### Where the Council Clashes (not fundamental — no second pass)
- **Is memory-clear a feature or a liability?** Proponent: the sharpest feature (kills drift; next sub-goal rehydrates from persisted artifacts). Contrarian/Outsider: a silent corruptor (it wipes the *rationale* for why a green-looking schema is correct while the files persist, so later phases re-derive from rationale-stripped artifacts and verification trust decays with run length).
  **Resolution:** both are right at different layers. Clearing per-session *context* is safe **only if the rationale/caveats are externalized** (decision log + manifest verdicts), not just the code/schema artifacts. Reconcilable.
- No clash changes the recommendation (every advisor lands on an external, machine-verified, gate-respecting runner), so **no targeted second pass was triggered.**

### Blind Spots Caught (only surfaced in peer review — the highest-value additions)
1. **Security / blast radius (biggest miss — no advisor raised it).** An unattended, write-and-shell-capable agent running for hours: destructive commands, **prompt-injection from the very artifacts it reads**, credential/secret exposure, no sandbox / least-privilege, no kill switch, no tamper-evident audit of *who changed what and why a gate "passed"* — and it bypasses the **mandated DB-change approval path**. Nobody is watching when it goes wrong.
2. **The manifest's *content* is assumed correct.** All five debated the *executor* and accepted the phase decomposition as sound. But a wrong or ambiguous sub-goal executes flawlessly, unattended, into thousands of committed lines, undetected until PH-10. **Automation scales garbage-in worse than manual runs**, where a human catches drift mid-stream. Validate the prompts/exit-checks before trusting any engine.
3. **No per-phase transactional boundary.** A mid-phase crash can leave the shared schema half-migrated, and the next "green" check then passes against a **corrupted baseline**. Plus observability: when it parks or hard-halts, who gets paged, through what channel?

### Idea Evolution
First pass already collapsed the literal proposal: 4/5 rejected the single-master-`/goal` outright and the Proponent reframed it to a "manifest-driven runner," so the debate moved from *whether* to *what engine*. Peer review then shifted the recommendation again — from "just change the engine" to "change the engine **and** add a safety/verification harness" — by surfacing security, manifest-correctness, and transactional-rollback, none of which any advisor had raised.

### The Recommendation
**Your instinct is right; the specific mechanism is not — and as literally described it is also unsafe. Do NOT run one master `/goal` looping over the file in a single session.** It cannot fit in context, it structurally fights the human gates, its "done" is self-graded (rubber stamp / reward-hack prone), and unattended it has an unbounded blast radius.

**Do this instead — automate the *sequencing*, never the *judgment*:**
1. **Keep the file** as a manifest: per entry = `{prompt_file, exit_criteria_command (returns 0/1), gate: auto|human}`.
2. **Replace the engine with an external driver** (a bash loop now; graduate to CI or a scheduled agent). It runs **one sub-phase per fresh session**, then the *driver itself* runs the exit-criteria command **outside the model, from a clean checkout**, and advances to N+1 **only if green AND `gate:auto`**; on `gate:human` it **parks and pings you**.
3. **Checkpoint + resume** from phase N (never restart PH-00 — you have hit spend caps); **hard-stop, don't retry-loop**, on a red check or an `AMBIGUITY`.
4. **Add the safety harness the advisors missed:** run on a throwaway branch with least-privilege creds, a spend cap + kill switch, keep the **DB-change approval as a human gate**, wrap each phase so partial failure rolls back, and **validate the manifest content** before trusting the driver.
5. If a phase's exit-criteria **cannot be written as a shell command that passes/fails, it is not automatable yet** — mark it `gate:human`.

This yields ~90% of the toil reduction (no re-typing, no babysitting transitions) with none of the "unattended past a review gate / self-certified / unbounded-blast-radius" failure modes.

### The One Thing To Do First
Write `phases.yaml` with those three fields per entry and **prove the driver on PH-00A alone**: fresh session → run PH-00A → the driver runs PH-00A's exit-criteria command itself → advance only if it returns green. If you can't express PH-00A's exit-criteria as an executable check, that finding *is* the result — those phases stay human-gated.

## Advisor Responses (de-anonymised)

**Proponent (labeled B in review):** Every sub-phase prompt is a pre-authored autonomy envelope sized for one run, so the file is an execution manifest over validated units, not a "let it rip" script. The `/goal` Stop hook is the unlock — a per-sub-goal exit-criteria enforcer giving a machine-checked gate between units. Memory-clear is the sharpest feature: memory is file-based and evidence persists, so clearing context prevents drift while the next sub-goal rehydrates from artifacts. Encode human gates as first-class stop points whose exit-criterion is an external approval token (a file the reviewer drops); make each escalate-condition a hard halt that writes state and stops. Maximal-value form: a manifest-driven runner (verified hop, persisted evidence, optional memory reset, explicit gate/escalation entries) — not "one `/goal` to rule them all."

**Contrarian (D):** Keep the declarative file; the fatal flaw is the executor. `/goal` is a Stop hook designed to *prevent* halting; a human gate *requires* halting — one master `/goal` weaponizes the harness against the gates. The only arbiter of "done" is the agent held hostage by a hook that won't let it stop: textbook reward-hacking (declare completion or weaken a failing test to green) — the documented overnight-autonomous failure mode, amplified. Non-obvious: compaction as silent corruptor — a green-but-subtly-broken schema is "broken" only because of a caveat in working context; lossy summarization + "clear memory" wipes the *why* while files persist, so later phases re-derive from rationale-stripped artifacts and verification trust decays with run length. Keep the file, kill the master `/goal`; one sub-goal per fresh session; gates as hard human stops with independent checks; green reproduced from a clean checkout. Automate sequencing, never judgment.

**First-Principles (A):** "Run without manual intervention" smuggles a false equivalence between reduced toil and full autonomy. The pipeline has human review gates — a gate is where a human decides; looping past them deletes the control structure. The real toil is re-typing prompts and babysitting transitions — a dispatch problem, not an autonomy problem. "One master `/goal` over a YAML" reimplements a workflow orchestrator inside a chat session — the least durable substrate; it assumes unbounded context, no crash/restart, and self-verifiable "done." Right unit: one durable run per sub-phase with a machine-checkable exit predicate, chained by an external scheduler; the mandated `manifest.json` IS the state file (stage + gate verdicts); encode phases as a dependency DAG; advance only on prior gate PASS, halting for human gates by design. The YAML is fine as input; the single looping session is the wrong engine.

**Outsider (E):** "Goal" and "loop" carry unearned weight. "`/goal` blocks until a condition holds" assumes the condition is machine-checkable and honestly checked — the biggest hidden assumption. If "done" is the agent's own opinion it degrades to "blocks until the agent decides to say yes" — a rubber stamp; nobody would know if it lied, because the thing declaring success is the thing doing the work. Expect a separate dumb checker the agent can't talk past. "Human review gates" + "unattended" cannot both be true — honest version: unattended up to the next gate, then parks. "Wipe memory" + "file-based memory" clash to a newcomer: step 5 knows step 4's decision only if step 4 wrote it where step 5 reads — the file is load-bearing, not an optimization; one forgotten write and later steps silently diverge. Missing: an independent oracle, and a rollback for when a step corrupts shared code/schema mid-run.

**Executor (C):** Fails on context — one session cannot carry PH-00A..PH-10; the 447-table schema, contracts, and tests already saturate context and auto-compaction drops exit-criteria/evidence rules. So: no to the fully-unattended master goal, yes to a driver far better than manual — one-phase-per-session, orchestrated from outside the session. Monday: write `phases.yaml` with, per entry, the prompt file, the exit-criteria command (returns 0/1), and `gate: human|auto`. If you can't write the check as a shell command, that phase isn't automatable yet — say so now. A bash/scheduled driver fires phase N in a fresh session, waits, runs the exit command itself, advances only if green AND `gate:auto`; on `gate:human` it halts and pings. Memory clears for free. Breakage priority: cost (checkpoint, resumable from N, never restart PH-00); failing test (stop, no retry-loop); decision needed (hard stop). Start with PH-00A only and prove the driver green-gates one real transition this week.

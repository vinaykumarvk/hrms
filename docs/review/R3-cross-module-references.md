# R3 — Cross-Module Reference Integrity Review

**Scope:** 14 platform-grounded government-HRMS BRDs (`docs/brd/v3/G01..G14*.md`).
**Concern:** one cross-cutting axis only — when module A says it consumes/feeds module B, does the referenced entity/event/FR actually exist in B and agree on direction and semantics?
**Date:** 2026-07-01 · **Reviewer:** integration-reviewer (report-only, no edits to BRDs).

---

## Verdict

The suite is **unusually well cross-referenced**: every module uses the canonical `G01..G14` code scheme, carries an explicit "Alignment with PrimeSoft Platform", integration-contract, and dependency section, and the *large structural* contracts reconcile cleanly on both sides — the G11→G12 service-verification gate (G12 FR-08/FR-13 ↔ G11 FR-18), the G09 penalty→G06/G10/G11/G12 downstream map, the G10-owns-increments / G06-mirrors agreement, the G13 polymorphic `:attach`/`:fetch` contract, and the G14 read-only mart model are all reciprocated. **The weak seam is the G12 SR write-path:** several upstream producers (G05, G06, G04, G02, G01) emit SR `event_type` strings or use a `source_module` identity that does **not** match G12's published taxonomy / per-source allowlist (Appendix B/C, FR-02 BR-02.1) — yielding dangling event types and one genuine ownership conflict (identity-change events claimed by both G01 and G02). Separately, the flagship **G03→G04 leave handoff disagrees on the correlation key** (`application_id` vs `leave_spell_lineage_id`) and on the signed-capture shape, two analytics feeds (G02/G04→G14) are not reciprocated by G14's source list, and one promotion-eligibility handoff (G07→G06) is advertised by G07 but not consumed by G06. No module is internally broken; the fix is a normalization pass centred on G12's taxonomy and the G03/G04 join key.

**Counts by severity:** High **4** · Medium **6** · Low **2** · Total **12**.

## What reconciled correctly (no finding)

- **G11 ↔ G12 verification gate** — G12 FR-08/FR-13 provides the signed-off/locked SR verification + single pull-feed; G11 FR-18 blocks all benefit calculation until `service_verifications.status = SIGNED_OFF/LOCKED`. Bidirectional, names match.
- **G09 → G06/G10/G11/G12 penalty effects** — G09's penalty→downstream map (sealed-cover/promotion freeze→G06, subsistence/recovery→G10, pension cut/Rule-9→G11, SR events→G12) is reciprocated by each consumer's boundary section.
- **G10 owns increments / G06 mirrors** — both sides agree G10 is system-of-record for increments and stepping-up; G06's `increment_monitor` is explicitly a mirror/monitoring view.
- **G13 attach contract** — `documents:attach` / `:fetch?intent=` polymorphic link `(module_code, entity_name, entity_ref_id, link_role)` is consumed consistently by G01–G12; lifecycle inbox (`EMPLOYEE_RETIRE/MERGE` from G01, `CASE_CLOSE` from G09, retire-confirm from G11) reciprocated.
- **G14 read-only marts** — G14 never writes source data / SR; reads via versioned `source_data_contract` + Debezium CDC; G12 SR read-only, G13 export-refs-only — all consistent with each owner's "G14 reads, never writes" statement (except the G02/G04 omission in F9).
- **G05 → G01 / G10 handoffs** — `POSTING_UPDATE`/org-placement to G01 and `PAY_CONTINUITY`/`LPC_REQUEST` to G10 are reciprocated by G01 (org owner) and G10 (pay executor).

## Method & confidence

Each module's Alignment, API/Integration, and Traceability/Dependency sections were extracted and the producer-side `event_type`/entity/API identifiers were cross-checked against the consumer-side catalog/allowlist (notably G12 §16.2/§16.3 and FR-02). High/Medium findings were verified against the literal strings in the source files (line numbers cited). Note that G12's launch catalog is marked "illustrative" and its taxonomy is versioned/extensible — so the event-name findings (F1, F4, F5, F10) are resolvable by taxonomy entries + allowlist edits rather than redesign, but they are real at the current specification level because G12 FR-02 BR-02.1 enforces `source_module ∈ allowed_source_modules` and type existence at ingestion.

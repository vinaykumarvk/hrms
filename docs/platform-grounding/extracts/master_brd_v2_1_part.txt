# 1. Executive Summary
Document positioning. This Business Requirements Document specifies what the system must do. It is read alongside the companion artefacts that specify how the system is designed, built, and operated, under the authority order in the Engineering Handoff — Start Here (RBAC → BRD → FS → Foundation/Platform Spec → prototype): the Clickable Prototype v2.6 is the authority for screens and flows (321 screens); the module and Foundation Functional Specs define screen behaviour, validations, and shared services; the named configuration exports define the complete field inventory and allowed values for each configuration screen; and the RBAC Design Document is the single source for roles, permissions, and field-level access. Physical implementation choices — database engine, application framework, cloud provider, object storage, messaging, search/indexing, secrets management, observability, and deployment topology — are owned by the engineering team within the logical architecture in Product Vision Part 2 and the Platform Specification, and within the non-functional targets in §1.5. Where this BRD and a companion document conflict on intent, the authority order above governs.

## 1.1 Project Name
PrimeSoft HRMS — Phase 1 (Foundation & Core Operations).

## 1.2 Project Description
PrimeSoft HRMS is a commercial-grade, enterprise-class Human Resource Management platform built as owned intellectual property of PrimeSoft Solutions, Inc. Phase 1 delivers the operational backbone of the platform: the complete hire-to-retire lifecycle (employee master, onboarding, exits), time management (leave, attendance), talent acquisition (recruitment ATS), performance management, document management, analytics, and IT asset management, supported by six cross-cutting platform modules (workflow engine, RBAC, AI chat agent, tenant administration, audit logging, migration toolkit). The platform is delivered as a responsive web application supporting three deployment models from a single codebase: Standalone (single organisation, single legal entity), Multi-Tenant SaaS (shared infrastructure with tenant-level data isolation), and Group Company (one parent with multiple legal entities sharing one HRMS instance).

## 1.3 Business Objectives
Own vs Rent — Eliminate perpetual subscription dependency. Built once, owned permanently. Operational costs reduce to hosting and maintenance, not per-employee licensing.
Migration Advantage — Provide a structured, tooled migration pathway from Darwinbox (the primary source system for Release 1 migration) with less than 0.5% data error rate on Dry Run 3.
Configuration over Code — Serve any industry segment and geography through configuration, not customisation. Segment and geography selection at provisioning drives all defaults.
Compliance First — India’s statutory compliance landscape (EPF, ESI, TDS, PT, LWF, Gratuity, POSH, DPDPA, Shops & Establishments) is a first-class concern, built into the data model from Day 1.
SaaS Readiness — Onboard a new tenant in hours through automated provisioning and segment-driven default loading.
AI Native — Intelligence embedded in the core. Every module benefits from AI-assisted guidance and insight via the document-grounded Chat Agent.

## 1.4 Target Users and Pain Points
Phase 1 Release 1 target: IT Services organisations operating in India with up to 500 employees per tenant, transacting in Indian Rupees, with English as the working language.
Primary user constituencies and their pain points:
| User | Pain points addressed |
| Head of HR | Lack of single source of truth across HR data; inability to consolidate multiple legal entities; perpetual SaaS licence fees with no data ownership. |
| HR Administrator | Manual reconciliation between onboarding, payroll, and statutory filings; absence of audit-grade trails for every data change; difficulty enforcing PII protection at field level. |
| Hiring Manager / Recruiter | Disconnected ATS, no integrated offer-to-onboarding handover, fragmented BGC vendor management. |

### 2.1.3 Indian Statutory Compliance (Phase 1 elements only)
Full statutory deduction calculation and government filing outputs (PF/EPF, ESI, TDS, PT, LWF, Gratuity payout) are Phase 2 (M06 Payroll + M07 Statutory Compliance) and out of scope for Phase 1. Two statutory obligations are embedded in Phase 1 modules:
POSH Act 2013 — Mandatory policy publication and acknowledgement · Complaint intake via M01 Grievance Register (anonymous opt-in) · ICC routing for POSH-category grievances · Training completion tracking via M11.
DPDPA 2023 — Consent capture at onboarding · Right of access (employee can export their own record with PII unmasked) · Right of correction (via sensitive-field change workflow) · Right of erasure (non-statutory data only, statutory data has legally mandated retention) · Data principal request register · Data fiduciary obligations · Audit log redaction marker for erased PII.
Shops & Establishments Act — State-wise leave entitlements and working hour rules · Location-based policy overrides.

# 3. User Roles & Permissions
[RBAC — single source of truth] The RBAC Design Document v1.7 is the authoritative single source for the access-control model: role taxonomy, the permission matrix, field-level access, capability flags, individual entitlements, and User Assignment Groups. Sections 3.2–3.10 below are retained as business context; where they differ from the RBAC Design Document, the RBAC Design Document governs. Phase-1 capability flags are four — BGV review, Letter Admin, Asset Custodian, and Department Head — Asset Audit Certify — plus two HOD configurable grants (report visibility; per-workflow approval authority). Change Manager is not a Phase-1 flag.

## 3.1 Role Taxonomy Overview
PrimeSoft HRMS Phase 1 defines 18 distinct roles spanning platform administration, organisational administration, HR operations, module administration, manager hierarchy, specialist functions, and individual access. A user may hold more than one role simultaneously. Where a user holds more than one role, the more restrictive permission applies — a less permissive role never elevates access granted by a more permissive one (Conflict Resolution Rule). Exception — defined inheritance: HR Admin is a defined superset of the nine operational module-admin roles (§3.1.1); its inherited permissions are part of the HR Admin role definition itself, not a multi-role combination, so the Conflict Resolution Rule does not down-scope HR Admin to a module admin’s narrower reach.
Access control operates at four layers, applied in combination for every user session: (a) Module-level — whether a module is visible at all; (b) Field & Section level — visibility and editability of fields and form sections; (c) Data-level (row-level security) — which records a role can see, scoped by reporting chain, department, contribution level, UAG, or entity; (d) Action-level — what a user can do within a record (View Only, Edit, Approve/Reject, Download, Admin Rights).
PII Protection Ceiling — PII fields carry system-enforced protection ceilings. No Organisation Admin, Module Admin, or any other role can override these ceilings upward. Exceptions are explicit platform-level grants (e.g. Office Admin national ID access) and are fixed — not configurable.

## 3.3 Entity-Scoped Operational Roles
Entity scope reminder. All roles in this section operate within a single legal entity. The HR Administrator, Finance Admin, HRBP, Office Admin, CEO, and the module-specific admins (Onboarding, Offboarding, Leave, Attendance, Performance, Document, Recruitment) all have single-entity scope. No HR transaction crosses entity boundaries — every leave application, separation, payroll run, statutory return, and employee record edit stays within the entity that owns the employee. Cross-entity visibility within a tenant is owned by Org Admin alone (see §3.2 Platform Roles). Platform Super Admin is cross-tenant, not cross-entity — it should not be used to bridge entities within a single tenant. If an HR Administrator needs cross-entity insight (e.g. a group-wide attrition report or to check whether a separated employee from Entity A has been rehired into Entity B), the request is routed to Org Admin, who provides the consolidated view.
Entity scope reminder. All operational roles in this section are scoped to a single legal entity within the tenant. In a Group Company deployment with multiple entities (e.g. a holding company with subsidiaries across geographies — Solutions Pvt Ltd in India, Global Inc in the US, Services Pte Ltd in Singapore), each entity is staffed with its own HR Admin, Finance Admin, Office Admin and module admins (Onboarding, Leave, Attendance, Performance, Document, Offboarding, Recruitment). No transactional flow crosses entity boundaries — every leave application, attendance regularisation, payroll component, statutory filing, separation FnF, and grievance stays within the employee’s entity of record. Cross-entity activities (group headcount reports, group attrition, ex-employee lookup across entities, internal mobility scouting across entities) are owned by Org Admin per §3.2; HR Admin is not the channel for cross-entity visibility. Platform Super Admin is cross-tenant (all customers) and is also not the channel for cross-entity visibility within a single tenant.

### 3.1.1 HR Admin as the operational superset role
HR Admin is the single operational superset role within an entity. Every permission held by any of the nine module-specific admin roles is also held by HR Admin. This means HR Admin can directly perform every configuration, approval, override, and oversight action that the following roles can perform, without needing the module-admin role to be separately assigned:
| Module admin role | Module | Functions HR Admin inherits |
| Recruitment Admin | M08 | Full ATS visibility · requisition management · recruiter assignment · pre-offer issuance · document review · offer letter generation · pipeline oversight · recruitment reporting |
| Onboarding Admin | M02 | Configure onboarding checklists · task assignments · buddy assignments · BGV vendor profiles · verification packages · onboarding completion tracking |
| Leave Admin | M04 | Configure leave types / policies / accrual rules · override balances · manage holiday calendar · approve and reject leave requests · (plus HR Admin’s exclusive encashment authorisation) |
| Attendance Admin | M05 | Configure shifts and rosters · biometric device mapping · lock / unlock attendance periods · override punch records · approve and reject attendance request types |
| Document Admin | M11 | Configure policy library register · policy clusters and acknowledgement requirements · letter template register and merge fields · employee document vault settings · sign-off engine · versioning rules |
| Performance Admin | M09 | Configure appraisal periods and cycles · manage goal frameworks · initiate and close cycles · manage calibration sessions · (jointly owns appraisal-period definition with Performance Admin per FR-M09-001) |
| Offboarding Admin (Exit Admin) | M03 | Configure FnF clearance workflows · exit interview templates · separation checklists · offboarding completion tracking · (plus HR Admin’s FnF settlement authority) |
| Office Admin | M01 | Employee directory · date-of-birth view · national ID view and upload (PAN, Aadhaar, Passport, Driving Licence) · bank account entry and update |
| Analytics Admin | M16 | Create and publish custom report definitions · schedule report delivery · manage dashboard layouts (entity-scoped) |

Rules governing the superset:
Inheritance is one-directional. HR Admin ⊇ each module admin. No module admin inherits HR Admin’s broader permissions (e.g. Leave Admin cannot do recruitment tasks; Onboarding Admin cannot do attendance tasks).
Module admins remain assignable for delegation. An entity may still appoint a dedicated Leave Admin, Attendance Admin, etc. to distribute operational load. The superset relationship does not remove the module-admin roles — it means HR Admin does not require them to act in those areas.
PII protection ceilings still apply. The superset does not elevate HR Admin above any system-enforced PII ceiling. HR Admin’s PII access is governed by §3.1’s PII Protection Ceiling rules, not widened by inheriting module-admin permissions.
Entity scope is preserved. HR Admin’s superset applies only within their own entity. Cross-entity visibility remains with Org Admin per §3.2 — inheriting module-admin permissions does not grant cross-entity reach.
Joint-authority patterns are unaffected. Where a function is explicitly joint (offer letter generation with Recruitment Admin; appraisal-period definition with Performance Admin), HR Admin’s inherited permission satisfies one side of the joint authority; it does not bypass approvals that require a second distinct role (e.g. CEO co-signature on above-threshold offers).

## 3.6 Data Scoping Dimensions
Five dimensions can be combined to define what records a user can see:
Reporting Chain — Manager roles see records of their direct and indirect reports only. Skip-level Managers see their full subtree but cannot approve or edit.
Department — HOD sees all employees in their assigned department regardless of reporting line.
User Assignment Group (UAG) — A named group of one or more employees, optionally scoped to a project and its locations. Created and managed by HR Admin or Organisation Admin. An employee belongs to at most one UAG. UAG is an RBAC (access-control) construct only — it defines who can see and act on a population (e.g. UAG Head scope). It does NOT carry leave, shift, or holiday entitlement; those are assigned via the Assignment Framework (§4.2.17). UAG Head has same entitlements as HOD scoped to their group, except workflow approval authority (hard ceiling).
HRBP Assignment — HRBPs are assigned employees directly, individually or via UAG. Data scope limited to directly assigned employees, refined by entitlement dimensions.
Contribution Level — Additional filter applied within a role’s normal scope. Levels: Intern, Associate, Individual Contributor, Lead, Senior Lead, Manager, Senior Manager, CEO. Used in performance calibration scoping, hike recommendation banding (Phase 2), and recruitment entitlement configuration.
Entity — HR Admin, Finance Admin, and Office Admin are scoped to their single entity. Cross-entity access requires explicit privilege granted by Organisation Admin and is audit-logged.
Individual Entitlement — Time-bound access beyond a role’s default profile, granted by Organisation Admin within PII protection ceilings. All individual entitlements require Org Admin approval, are audit-logged, carry a mandatory expiry date, and are automatically revoked on expiry.

## 3.10 Capability Flag Registry
Capability flags are grantable extensions to existing roles. A flag is NOT a role — it is an opt-in capability that an Organisation Admin grants to a specific user’s existing role assignment. Grant and revoke events are audit-logged to P05.
Skills & Assets visibility. An employee’s Skills / Competency Profile is visible to the employee, their management chain (L1–L5, HOD/UAG Head) for deployment and development decisions, but not to HR Admin, HRBP, or Finance Admin on the employee record. Assigned Assets are owned by IT Admin (M17) and are visible to the employee and their direct manager (via Team Assets); they are not surfaced on the HR Admin or HRBP employee-detail view — HR Admin engages with assets only for FnF recovery escalation (FR-M17-004). This keeps the HR employee record focused on HR-domain data and avoids HR seeing IT asset inventory or skills taxonomy by default.
FY26 HOD visibility revision. Education Qualifications and Certifications are visible to the HOD / UAG Head — in addition to the employee and the L1–L5 management chain — for development and deployment decisions, consistent with the Skills / Competency Profile rule above. Education and Certifications are visible to HR Admin, HRBP, Managers (L1–L5), and the HOD / UAG Head, plus the employee on their own record. By contrast, the Skills / Competency Profile and date of birth remain restricted: Skills are visible to the employee and the L1–L5 / HOD chain but not to HR Admin, HRBP or Finance; date of birth is visible only to HR Admin, Office Admin and the employee (no manager, HOD, HRBP, peer or social-surface visibility, and no year-masking). Previous-employment, references and languages follow the same chain visibility as Education / Certifications; the statutory detail entities (PF / EPS / ESIC / gratuity / LWF / PT / insurance) are visible to the employee, HR Admin and Finance / Payroll Admin only. Full per-entity rows are added to the §3.9 matrix in the M01 functional specification. This revision also flips Probation Status, Confirmation Date, Contract Start Date, Contract End Date, Notice Period, and Previous Employment History from H to V for the HOD / UAG Head in the field-level access matrix above.

# 4. Data Model
This section defines every entity in the PrimeSoft HRMS Phase 1 platform. Every entity supports soft-delete only — no hard deletes anywhere in the platform. Every entity carries the platform audit columns described below in §4.1. Every entity within a tenant context carries tenant_id (non-nullable); every entity holding organisational data also carries entity_id as a child of tenant_id. All foreign-key relationships are enforced at the database layer. Every entity migrated from Darwinbox carries a darwinbox_source_id column for permanent source-to-state traceability.

## 4.1 Platform Audit Columns — Required on Every Entity
Every entity below extends a base column set. To avoid repetition, the column set is defined once here and referenced throughout. Field tables in §4.2 onward show only the entity-specific columns; the audit columns are implied.

### 4.2.7 user_assignment_groups (UAGs)
Named group of one or more employees, optionally scoped to a project. Created and managed by HR Admin or Organisation Admin. A UAG may be project-scoped (tagged to a project and one or more of that project’s locations) or general-purpose. An employee can belong to at most one UAG (one employee, one UAG). When a UAG is project-scoped, the employees tagged to it must be allocated to that project. UAG is an access-control construct only and does not distribute leave, shift, or holiday entitlement — those resolve via the Assignment Framework (§4.2.17). (Historical note: earlier drafts bound policies to the UAG; this was reversed in v2.1 (removed fields: uag_leave_policy_id, uag_shift_id, uag_holiday_calendar_id, now removed).
| Field | Type | Required | Validation / Description | Default |
| uag_name | string(120) | Y | Display name. | — |
| uag_head_user_id | uuid | N | FK → users.id. The user designated as UAG Head for this group. | NULL |
| hrbp_user_id | uuid | N | FK → users.id. The HRBP using this UAG as their assignment mechanism (optional alternative to business-unit assignment). | NULL |
| description | text | N | Free-text description of the group’s purpose. | NULL |
| project_id | uuid | N | FK → projects.id. When set, the UAG is project-scoped; tagged employees must be allocated to this project. NULL = general-purpose UAG. | NULL |
| project_location_ids | uuid[] | N | One or more locations of the project this UAG covers (subset of the project’s delivery locations). | NULL |
| created_by_role | enum | Y | HR_ADMIN · ORG_ADMIN. Records which role created the UAG. | — |
| status | enum | Y | ACTIVE · INACTIVE. | ACTIVE |

Business rules:
One employee, one UAG. An employee referenced in uag_members for an ACTIVE UAG cannot be added to any other ACTIVE UAG. Attempting to tag an already-assigned employee returns a validation error naming the existing UAG; the employee must be removed from the current UAG first.
A project-scoped UAG can only tag employees allocated to its project_id; project_location_ids must be a subset of that project’s locations.
Leave / shift / holiday bindings on the UAG apply to every member as the assignment unit; a per-member override follows the standard assignment precedence.
HR Admin operates within their entity; the UAG’s project (if any) must belong to the same entity.

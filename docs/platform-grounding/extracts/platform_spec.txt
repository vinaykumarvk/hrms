## 0. Foundations (cross-cutting, underpin all services)
References: BRD §4.2 (tenancy/org entities), §7.4 (security NFR), Appendix C (audit); RBAC doc (session roles); Foundation FS §1 (API conventions).
0.1 Multi-tenancy &** isolation.** Every business table carries tenant_id and (where entity-scoped) entity_id. All data access is scoped at the data layer by the authenticated session’s tenant and entity; cross-entity reach exists only for Org Admin (RBAC §2.1) and is applied as a widened scope filter, never a bypass. Cross-tenant reach exists only for Platform Super Admin. Isolation is enforced in the persistence layer so an application bug cannot leak across tenants. Failure mode: a query without a resolvable tenant scope is rejected, not defaulted to “all”.
0.2 Authentication &** session.** Bearer-token session carries the user’s resolved roles and tenant/entity scope (model per RBAC doc). Token expiry, refresh, and concurrent-session policy per BRD §7.4; the session never carries raw permissions — they are resolved per request by P02.
0.3 Configuration management. Config entities (workflows, approval/skip/SLA settings, forms, policies) are versioned. On save they pass a validation step (per the relevant FR, e.g. FR-P01-001 workflow validation) and are rejected if invalid. Activation is immediate for new instances; in-flight instances continue on the version they started with (see P01, W.1). Config changes follow the cascade platform default → tenant → entity → employee (BRD §5.1.4); a higher-level change does not silently overwrite a lower-level override.
0.4 Service-contract conventions. Every internal service call carries the auth context (0.2), an idempotency key for state-changing calls, a correlation id, and returns the standard error envelope (Foundation FS §1; BRD §6.2). All P0x contracts below inherit this and do not restate it.
0.5 Observability standard. Every service emits structured logs (with correlation id), metrics (latency, error rate, throughput), and traces. Security-relevant events go to security_audit_log; data mutations to audit_log (Appendix C). Job runs and notification deliveries emit their own metrics (X.1, X.2).

## P01. Workflow Engine
References: BRD §5.1.1 (FR-P01-001…), §4.14.1–.3 (workflows, workflow_instances, workflow_actions), §4.14.12 (skip_settings), Appendix D (pattern reference), Appendix I (configured catalog). RBAC doc (approver resolution). The configured FLOW DEFINITIONS that run on this engine are modelled in §W.1; per-module triggers are in each module FS.
Engine responsibility. One engine drives all approval and notification processes across modules (FR-P01-001). This section authors how it runs; it does not restate the five patterns (Appendix D) or the FRs.
Definition &** version model.** A workflows row holds workflow_code, pattern, stages_definition, sla_definition. On save the engine runs validation (≥1 stage, every stage has an assignee-resolution rule, SLA defined, no circular stage reference) and sets status=ACTIVE (per FR-P01-001). Deprecation, not deletion, is the only path when instances are active. In-flight versioning: each workflow_instance pins the definition version it began on; deprecating/replacing a definition affects only new instances.
Pattern execution (references Appendix D): SEQUENTIAL advances one stage at a time; PARALLEL_ALL_OF opens all branches and joins only when every branch completes; PARALLEL_ANY_OF completes on the first approval and cancels the losing branches; CONDITIONAL evaluates its branch predicate against instance context at the moment the stage is reached; DYNAMIC_APPROVER resolves the approver set at runtime. The engine authors the join/cancel/evaluation-timing mechanics here; the pattern semantics stay in Appendix D.
Approver resolution (four mechanisms — references RBAC). Named role, reporting-chain position, named individual, cost-centre head. “Manager” resolves to L1 Manager, with the BRD’s stated fallback when L1 is absent. HOD / Skip-level / Dotted-line do not get approval authority by default; HOD authority is the per-workflow, per-user capability toggle granted by Org Admin (RBAC §4.3 / OPEN-RBAC-03). A named-individual approver who is inactive surfaces a configuration error at next instantiation (FR-P01-001).
Instance state machine, decision matrix &** skip-settings.** workflow_instances move through stages writing one workflow_actions row per action; decision-matrix and skip_settings (§4.14.12) are resolved at stage entry to decide routing/skip. Send-back re-routes to a prior stage and re-triggers only the affected stages.
SLA &** escalation runtime.** SLA timers per stage (sla_definition); on breach the engine emits an escalation event → notification (X.2) + audit, and applies the configured breach output (delegate/auto-act) from the SLA setting (W.1). Idempotent stage-advance: a double-clicked or retried approve produces one action, not two (idempotency key, 0.4).
Service contract.
Service: WorkflowEngine.startInstance (implements FR-P01-001) Callers: M01 sensitive-field change, M02 onboarding, M03 separation, M04 leave, M05 attendance/OT, M08 requisition/offer, M09 review — by reference from each FS Input: { workflow_code, subject_ref, context{…}, initiator } — auth/idempotency per §0.4 Output: { instance_id, first_stage, assignees[] } Errors: 400 invalid/inactive code · 403 (ref P02) · 409 duplicate (ERR-DUP-INSTANCE) / circular · 422 validation Events: instance.created → audit + notifications (X.2)
Also: advance/approve/reject/sendBack/delegate/cancel/query, each idempotent, each emitting one workflow_actions row + audit.
Commonly-missed: delegation/reassignment; initiator recall; ALL_OF join + ANY_OF loser-cancel; editing the subject record while an instance is in flight (locked or re-validated); behaviour when a definition is deprecated mid-flight (instance continues on pinned version).

## P02. RBAC & Security (enforcement engine)
References: BRD §5.1.2 (FR-P02-001/002), §3.6 (scoping), §3.7 (matrix), §3.9 (field access), §3.10 (capability flags); RBAC Design Document (the MODEL). This section authors ENFORCEMENT only — it never redefines roles, the matrix, field access, or flags.
Enforcement is model-driven. The roles, matrix, scoping rules, field access, and capability flags are owned by the RBAC doc and are referenced, not restated.
Administration surface (added v1.2). The RBAC model is administered through two Org Admin screens — cfg-rbac (roles list + role × permission matrix across all module groups) and cfg-rbac-role (the role permission editor: role definition plus per-module action toggles and scope selectors, with saves written to security_audit_log) — specified in RBAC Design Document §4.4. Those screens bind the model; this section authors only its enforcement. FR-P02-001/002 here denote enforcement (authorization resolution; field-level enforcement) and are distinct from the administration screens, which carry the RBAC §4.4 reference.
Permission-check resolution order (authored):
Check: on Resolution: deny-by-default → role grant (RBAC §5.1 matrix) → Conflict Resolution Rule: where a user holds multiple roles, take the INTERSECTION (more restrictive) of permissions (FR-P02-001) → individual entitlement (RBAC §3.2, time-bound; expiry auto-removed by a scheduled job) → capability flag (RBAC §4.3) → PII Protection Ceiling: overrides everything; no role/combination lifts it upward (fixed Office Admin national-ID/DOB grants are the only platform-level exception, FR-P02-001) → data scope filter (RBAC §3.6 dimensions) → field mask on serialization (BRD §3.9 / Appendix B PII tiers) Failure: 403 ERR-FORBIDDEN + security_audit_log entry
Field-level enforcement (FR-P02-002). Every endpoint validates session token → module permission → field permission before responding; masking is applied on serialization so an over-broad query still cannot leak a masked field. Each role change/removal writes security_audit_log (event_type=RBAC_CHANGE).
Authorization service contract.
Service: Authorization.check (implements FR-P02-001/002) Callers: every module API + WorkflowEngine approver resolution Input: { subject(roles,scope), action, resource_ref, fields[] } Output: { allowed, scope_filter, field_mask[] } Errors: 403 (deny) with audit; never reveals existence of out-of-scope records (404-style)
Commonly-missed: row-scope application point (data layer); admin/impersonation bypass and its auditing; rate-limiting/lockout (BRD §6.3/§7.4); token/secret rotation; the Office-Admin-on-own-record edge case (FR-P02-001).

## P03. Chat Agent (AI)
References: BRD §5.1.3 (FR-P03-001/002), §4.14.11 (ai_chat_queries), Appendix B (PII). RBAC doc (data scope, PII ceiling).
Grounding &** retrieval.** Answers only from (a) org-uploaded HR policy/statutory documents and (b) the user’s own permissible data; on no relevant passage, returns the explicit “I don’t have information about that in your organisation’s documents” response (FR-P03-001). Retrieval freshness tracks document updates. The assistant additionally answers HRMS usage guidance (“how do I do X in the app”) scoped to the user’s role, and knowledge-base articles — the knowledge base is answered here, so there is no separate KB surface. All responses are role-scoped (bound by the requester’s field/module visibility). A prioritised roadmap of agentic capabilities (apply leave / regularise attendance by chat, raise a ticket, show balances/payslip, summarise tasks & approvals) is surfaced as “coming soon”; Release-1 outputs remain informational-only and the assistant is mobile-responsive (NFR §7).
Guardrails &** PII.** All AI calls are backend-only; the API key never reaches the client. PII is stripped server-side before any model call, governed by the same PII ceilings as P02 (government identifiers, financial fields, etc. never sent). Outputs are informational only — they never trigger workflows or automated actions. Per-tenant knowledge isolation. Pre-joining access per FR-P03-002.
Service contract &** logging.**
Service: ChatAgent.query (implements FR-P03-001) Input: { user_ctx, question } (PII-stripped server-side before model call) Output: { answer | no-information, source_refs[] } Logging: ai_chat_queries — METADATA ONLY; query/response CONTENT is not logged (FR-P03-001) Failure: AI API unavailable → graceful message, platform unaffected; latency target < 8s, interim “still working” message past threshold

## P04. Tenant & Org Admin
References: BRD §5.1.4 (FR-P04-001/002), §4.2 (org entities), §4.14.6 (integration_credentials). RBAC doc (Platform Super Admin vs Org Admin).
Provisioning lifecycle. A tenant is provisioned and operational within one business day: creates a tenants row, cascades segment+geography platform defaults (leave/performance/attendance/pay models), creates the initial Org Admin with forced first-login password change, and audit-logs all choices (FR-P04-001). Segment/geography are immutable post-provisioning (segment change ⇒ data migration); additional geographies can be added per entity. Standalone→Multi-Tenant / →Group-Company is a config change, no migration. Blocked if segment+geography master data is incomplete.
Config propagation &** effective-dating.** Config cascade platform→tenant→entity→employee; changes propagate downward except where a lower level holds an override. Effective-dated config changes apply to in-flight data per the owning module’s rule (reference; jobs in X.1).
Device/location registration (FR-P04-002). Biometric devices and IP-based attendance restrictions are registered here before use by M05.
Integration credentials. integration_credentials stored encrypted; rotation and per-integration scoping owned here (used by X.3).

## P05. Audit & Compliance Log
References: BRD §5.1.5 (FR-P05-001), Appendix C (structure — two logs), §4.14.4/.5 (audit_log, security_audit_log), §4.14.7 (consent_records). RBAC doc (who may read audit). Column structure is per Appendix C and is NOT restated here.
Capture mechanics. Every INSERT/UPDATE/soft-DELETE on any business table fires a database trigger writing one immutable row to audit_log — not application code, so no API bypass or bug can suppress it (FR-P05-001, Appendix C.1). 100% mutation capture, zero gaps. audit_log grants no UPDATE/DELETE to any DB user; the sole permitted mutation is a DPDPA right-to-erasure redaction marker on old_value. PII is stored masked in audit rows (raw PII never written). Reading an audit log is itself an audited action.
security_audit_log. Auth and permission events (login, RBAC_CHANGE, permission denials). Org Admin may query within tenant.
Retention &** tamper-evidence.** Minimum 7 years; entries archivable to cold storage after 2 years but queryable within 24h; exportable as structured data for regulators. Tamper-evidence via append-only + (proposed) periodic hash-chaining (see Z).
Consent (DPDPA). consent_records capture lifecycle (grant/withdraw); right-to-erasure redaction is the only audit overwrite path.
Query/export contract.
Service: Audit.query / Audit.export (implements FR-P05-001) Input: { filters(table, record, actor, date), scope } (read is itself logged) Output: { rows[] (PII masked per viewer tier), export_ref } Access: per RBAC (DPO / Org Admin within tenant)

## P06. Migration Toolkit
References: BRD §5.1.6 (FR-P06-001), Appendix E (wave detail), §11 (migration & launch), §4.14.9 (migration_runs). Waves and approach are referenced; the framework is authored.
ETL+V framework. Extract → Validate → Transform → Load → Verify, scripted idempotently (re-running yields the same result, FR-P06-001). Every migrated table carries darwinbox_source_id (permanent traceability + dedup key). Three mandatory staging dry runs gate production cutover.
Waves (reference Appendix E): Wave 1 (employee master, org structure, leave balances + 2-yr history, …) completes before Phase-1 go-live; Wave 2 (performance history 4 cycles, job history, contracts, …) before/concurrent; Wave 3 (payroll history, Phase 2) zero-tolerance on numeric discrepancies. Authored here: profiling, the field-mapping framework the FS mappings consume, reconciliation tolerances, the migration_runs ledger, rollback/re-run, and cutover freeze. Failed records are logged with source row + the violated rule. Darwinbox kept read-only ≥ 4 weeks post-go-live. Access: Platform Super Admin (tenant-level) + HR Admin (entity-level data) per FR-P06-001.

## Manager-role review (Round 3)
P01 — bulk actions on approval/task queues: approval queues support multi-select with bulk approve / reject / delegate. A bulk action is an iteration of the same single-item permission; partial failures are reported per row (the batch does not fail wholesale); bulk reject takes one shared reason. Applied in Prototype v2.2 to the high-volume queues (Leave, Regularisation, Check-in, Comp-off). Decision queues (appraisal moderation, separation, probation) are individual-judgment and are intentionally excluded pending product confirmation.
P01 — task routing & taxonomy: goal-plan, check-in and review-stage actions are first-class task types in the unified Tasks aggregation. Each task routes to exactly one workspace (Me / My Team / Admin) so an admin-who-is-also-a-manager never sees the same task in two lists.
P02 / P03 — Workspace model: the platform exposes a Workspace switcher derived from the user's RBAC role holdings + has-reportees flag (Me / My Team / Admin). Admin is an exclusive workspace. Workspace switches are audit-logged. See OPEN-FS-FND-05 for the BRD §3.4 self-service exclusivity decision.

## Manager-role review (Round 3 follow-up)
Subject-scoped profile shell / employee-context switch. The profile/workspace surface is rendered by a single component parameterised by subject employee + viewer context (self | manager | admin). Selecting a reportee sets the active subject and switches context (banner + breadcrumb), Team remains the active workspace, and the same component renders the employee's full tab set scoped to that subject with viewer-gated actions/fields.
